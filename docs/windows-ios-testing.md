# Проверка на Windows и iOS

Статус: подготовлены экспериментальные VLESS-профили XHTTP + REALITY (`stream-one`) и TCP + REALITY + Vision. Передача данных проверена внешним Linux-клиентом Xray 26.10.21 с fingerprint `firefox`; импорт и работа конкретных приложений Windows/iOS ещё не подтверждены. Это ручной протокол испытаний, не готовая VPN-подписка и не автоматическое переключение.

## Получение профилей

Оператор выдаёт каждому устройству отдельную пару ссылок `vless://`: `xhttp.txt` и `tcp-vision.txt`. В пределах пары UUID одинаковый, у разных устройств — разный. Файл `profiles.txt` содержит обе ссылки, по одной в строке. Ссылки дают доступ к серверу: передавайте их только через согласованный защищённый канал. Не вставляйте в публичные issue, онлайн-конвертеры, генераторы QR, журналы и скриншоты. После импорта очистите буфер обмена и удалите лишние копии.

Временный стенд может иметь отдельные нестандартные порты. Не заменяйте их на 443/8443. Срок окончания и процедура отзыва сообщаются в приватной инструкции. При остановке стенда или истечении срока проверка должна завершаться ошибкой; это не означает неисправность приложения.

Перед тестом зафиксируйте версию ОС, приложения и встроенного ядра, время с часовым поясом и тип сети. Метки устройств/сетей в публичных результатах должны быть обезличены.

## Windows

1. Установите v2rayN из [официальных релизов](https://github.com/2dust/v2rayN/releases), выбрав пакет для архитектуры системы с Xray. Зафиксируйте точные версии приложения и Xray. Версия серверного ядра сама по себе не подтверждает совместимость клиентского ядра.
2. Скопируйте содержимое `xhttp.txt`, импортируйте VLESS-ссылку из буфера обмена через меню серверов (названия пунктов зависят от версии). Выберите Xray как ядро. Импортируйте `tcp-vision.txt` отдельно.
3. Проверьте поля после импорта: у XHTTP транспорт `xhttp`, режим `stream-one`, путь из ссылки, REALITY, SNI, shortId, публичный ключ/password, fingerprint `firefox`; поле flow пустое. У резервного профиля транспорт TCP/RAW, REALITY и flow `xtls-rprx-vision`. Адрес, порты, UUID и ключ должны совпадать с приватным файлом. Не публикуйте эти поля.
4. Для первого теста используйте локальный SOCKS-прокси приложения, без TUN. Выберите XHTTP, включите ядро и узнайте фактический SOCKS-порт в настройках.
5. Выполните PowerShell-команду ниже, подставив только локальный порт. Запрос явно идёт через SOCKS с удалённым разрешением DNS; при ошибке прокси не повторяйте его напрямую.

```powershell
$ProxyPort = Read-Host 'Локальный SOCKS-порт приложения'
curl.exe --fail --show-error --connect-timeout 10 --max-time 30 --proxy "socks5h://127.0.0.1:$ProxyPort" --noproxy "" https://example.com/
```

6. Получение страницы Example Domain без отключения проверки TLS — положительный результат HTTP-проверки. Отключите XHTTP, выберите TCP/Vision и повторите. Затем остановите ядро и повторите команду: ожидается ошибка соединения с прокси.
7. Только после этих проверок отдельно включайте системный прокси или TUN. Проверьте браузер, DNS/IPv6, переключение сети и разрыв туннеля. Системный прокси не охватывает весь трафик. Автоматические прямые маршруты и bypass необходимо учитывать при интерпретации результата.

## iOS

1. Установите Happ по ссылке для iOS из [официального репозитория разработчика](https://github.com/HappDev/happ_su). Доступность зависит от региона App Store. Это кандидат для проверки, совместимость конкретной версии ещё не установлена.
2. Получите приватную пару для iOS через защищённый канал. Скопируйте одну VLESS-ссылку, откройте добавление конфигурации (`+`) и импорт из буфера обмена. Возможен локальный QR-импорт, если QR сформирован доверенным инструментом без передачи ссылки внешнему сервису. [Документация импорта Happ](https://www.happ.su/main/dev-docs/examples-of-links-and-parameters).
3. Импортируйте вторую ссылку отдельно. Сверьте поля по пункту 3 раздела Windows. Если приложение удалило `mode`, изменило fingerprint или не поддерживает XHTTP/REALITY, отметьте несовместимость версии; не считайте успешный импорт доказательством подключения.
4. Выберите один профиль вручную, используйте маршрутизацию тестового HTTPS-трафика через него, разрешите создание VPN-конфигурации iOS и подключитесь. Откройте `https://example.com/` в Safari. Повторите с другим профилем.
5. Отдельно проверьте Wi-Fi и мобильную сеть: каждый из двух профилей в каждой сети. Не включайте оба одновременно. Запишите задержку подключения, загрузку страниц, ошибки и повторяемость, не копируя профили в отчёт.
6. Отключение VPN на iOS может вернуть прямой интернет. Одна страница в Safari не доказывает работу туннеля или kill switch: для более строгой проверки оператор должен наблюдать запрос на контролируемой конечной точке или отключить тестовый сервер при активном VPN и проверить отказ новых запросов. Если приложение позволяет прямой маршрут, такую проверку помечают как провал защиты от прямого выхода.
7. Защиту DNS, IPv6, WebRTC и поведение при смене сети проверяют отдельно с доверенными конечными точками. Не заявляйте, что устройство полностью защищено, на основании одного HTTP-запроса. Не отправляйте диагностические данные сторонним сервисам без понимания их содержимого.

## Отзыв, сбой и завершение

Оператор удаляет UUID выбранного устройства из обоих inbound, валидирует конфигурацию и перезапускает только тестовый экземпляр. Тестируют новое соединение; удаление записи без перезапуска не применяет изменение, а старые сессии могут сохраняться. Отзыв токена подписки не заменяет отзыв UUID.

Для каждого устройства после отзыва оба профиля должны перестать устанавливать новые соединения. Другое устройство проверяется отдельно. После завершения удалите профили и сохранённые VPN-настройки, остановите отдельную тестовую службу и удалите её приватные данные. Существующие SSH, firewall, Tor и другие службы для этого изменять не требуется.

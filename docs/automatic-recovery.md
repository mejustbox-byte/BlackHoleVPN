# Автоматическое восстановление процесса и безопасный запуск узла

Состоит из двух независимых частей: `blackhole.recovery prepare` выполняется перед **каждым** стартом выделенного Xray; `blackhole.recovery watch` работает отдельной systemd-службой и восстанавливает незавершённые операции. [Шаблон Xray unit](../examples/systemd/blackholevpn-node.service), [шаблон supervisor](../examples/systemd/blackholevpn-recovery.service).

## Что защищает запуск после загрузки

`ExecStartPre` работает до старта Xray и не вызывает restart/start самого себя. При свободном config lock он:

1. Проверяет привязку policy к фактическому ExecStart.
2. Загружает last-good и **актуальный** независимый реестр устройств.
3. Собирает разрешения только из active-записей, проверяет и приватно публикует безопасную конфигурацию.
4. Записывает `recovering`; здоровье не объявляется подтверждённым до сетевых probes supervisor.

Прежний кандидат, отозванные UUID в last-good и оставшийся после аварии ticket не являются источником разрешения. Если реестр/маркер/last-good отсутствуют, небезопасны или повреждены, pre-start возвращает ошибку: Xray не запускается. Ошибка не вызывает автоматический `registry-init` и не сбрасывает историю отзыва.

При наличии правильного pre-start и `Restart=on-failure` сам systemd перезапускает упавший Xray, но сначала вновь выполняет эту проверку. На загрузке supervisor стартует после Xray через `After=`; `Wants=` не запрещает supervisor попытаться восстановиться, если первый запуск Xray не прошёл.

## Как не получить deadlock во время apply

Apply удерживает config lock во время systemctl restart. Его дочерний `ExecStartPre` не должен ждать ту же блокировку.

Перед restart оператор создаёт приватный `.server.json.start-ticket.json`: точные SHA256 конфигурации/реестра, PID управляющего процесса, время его старта из `/proc`, boot ID. Ticket не содержит ключей/UUID, но всё равно хранится с `0600`. Guard при занятой блокировке проверяет реального владельца flock через `/proc/locks`, живой PID и время старта, boot ID, поколения файлов, соответствие authority и синтаксис Xray. Только тогда возвращает `delegated` без повторного захвата lock и без перезаписи конфигурации.

После restart ticket удаляется. При SIGKILL, освобождённом lock, повторном использовании PID или новом boot ID старый ticket не даёт разрешения. При свободном lock он всегда игнорируется в пользу last-good и актуального authority. Согласованные операции не могут изменить authority параллельно, поскольку lock по-прежнему у контроллера. Root/оператор, намеренно обходящий файловые проверки, остаётся вне модели защиты.

Поддерживается Linux с доступными `/proc/locks`, boot ID и метаданными процессов в том же PID namespace. Если окружение скрывает эти данные или разделяет PID namespace, механизм блокирует запуск вместо предположения о владельце lock. Это нужно проверить до включения на новом узле.

## Автоматический supervisor

```sh
python3 -m blackhole.recovery --policy /private/apply-policy.json watch --interval 5
```

На каждой итерации он пытается взять config lock без ожидания. Пока работает другой apply/CLI, возвращается `busy`, текущая операция не прерывается. После гибели контроллера flock освобождается ОС; `applying`/`recovering`, отсутствующий/повреждённый журнал, изменившийся PID или несогласованное поколение обнаруживаются на следующем цикле.

Supervisor либо подтверждает сетевым health-check уже согласованную last-good, либо запускает тот же безопасный rollback с повторным чтением реестра. После успеха кэширует поколение конфигурации, реестра, журнала и PID. Изменения authority, включая отзыв, требуют сверки и применения безопасных разрешений; простой файл CLI сам по себе не означает, что работающий процесс уже их применил.

При неизменном проверенном поколении проверяется состояние/привязка процесса без постоянных HTTPS-запросов. Это **не непрерывный сетевой мониторинг**: отказ передачи трафика без изменения PID/файлов может остаться до следующей отдельной проверки. Изменённое/новое поколение проверяется настоящими HTTPS-пробами обоих транспортов, без direct fallback.

Если authority/last-good недоверен либо recovery не подтвердился, выполняется попытка остановки только привязанного unit, фиксируется ошибка и повторные попытки идут с увеличением паузы до 60 секунд. Ошибка остановки не скрывается успешным статусом: требуется операторская проверка. Системные start-limit ограничения не сбрасываются кодом автоматически.

Сам supervisor запускается с `Restart=on-failure`: systemd восстанавливает его после SIGKILL. `KillMode=control-group` завершает дочерние пробники погибшего процесса. `.server.json.watch-state.json` (`0600`) содержит PID/boot/status для диагностики; это не источник разрешений и не доказательство актуального здоровья без сопоставления с живым процессом. Вывод приложения — только фиксированные статусы без конфигураций/токенов.

## Установка на отдельный узел

Шаблоны — примеры для **нового выделенного root-owned узла**, а не команда изменения произвольной работающей службы. Пути, бинарник, имя unit и policy необходимо согласовать. Config/authority/last-good/policy принадлежат оператору; каталоги `0700`, приватные файлы `0600`. Supervisor имеет привилегированное право управления этой службой. Делегирование non-root-пользователю требует отдельной безопасной настройки, здесь оно не автоматизировано.

1. Подготовить узел, реестр, probe-устройство и policy по [apply-инструкции](health-checked-apply.md). Пока нет last-good, включать pre-start guard нельзя: bootstrap намеренно закрыт.
2. Только на новом тестовом экземпляре однократно запустить проверенную конфигурацию **до** добавления ExecStartPre и выполнить `blackhole.apply ... adopt`. Подтвердить фактический запуск текущего файла и HTTPS через оба транспорта.
3. Установить адаптированные unit-файлы, теперь включая guard. Пример Xray разрешает pre-start запись только в приватный каталог через `ReadWritePaths`; без этого `ProtectSystem=strict` помешает публикации безопасной конфигурации.
4. Выполнить `systemctl daemon-reload` и явный `blackhole.apply ... recover`. Убедиться, что делегированный pre-start не блокирует restart и оба probes успешны.
5. После проверки включить автозапуск **этих выделенных unit**, например:

```sh
systemctl enable blackholevpn-node.service
systemctl enable --now blackholevpn-recovery.service
```

6. Проверить SIGKILL управляющего процесса, supervisor и Xray; при подтверждённом доступе к консоли провести отдельное испытание настоящей перезагрузки нового узла. Перед подключением пользователей протестировать DNS/IPv6, внешнюю доступность и восстановление с внешней копии.

Для диагностики без фонового цикла:

```sh
python3 -m blackhole.recovery --policy /private/apply-policy.json once
```

Коды `once`: 0 — здоров/безопасно восстановлен; 5 — lock занят, ничего не применено; 4 — восстановление не подтверждено; 2 — предусловия/политика заблокировали операцию. `prepare` возвращает 0 только для prepared/delegated. Его нельзя заменять условием shell, игнорирующим ошибку.

## Границы проверки

[Результаты](validation-results.md) включают реальные SIGKILL/systemd-перезапуски, отдельный boot-like target, stale ticket, старую конфигурацию с отозванным UUID и отсутствие authority. Проверялся только запуск изолированных лабораторных unit; команда `systemctl isolate` и перезагрузка действующего VPS не использовались. Boot-order simulation не доказывает работу после настоящего kernel reboot, отключения питания, монтирования/расшифровки диска или отказа внешней сети.

Авторитетный реестр нельзя откатывать вместе с last-good. Root-компрометация, недоступный systemd, зависшая ОС, потеря диска, отказ внешней контрольной точки и ручной запуск Xray в обход guard требуют отдельной защиты. Возможны временные приватные файлы probes при SIGKILL; они остаются в защищённом каталоге и требуют ограниченной процедуры очистки. Автозапуск не означает нулевой простой или мгновенное завершение всех старых сессий.

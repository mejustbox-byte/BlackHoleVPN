# Реестр устройств и защита от возврата отозванных UUID

Реестр — отдельный источник разрешений для **одной управляемой конфигурации на одном узле**. Он хранит внутренний идентификатор устройства, имя, UUID и состояние `active`/`revoked`. Снимки Xray не являются источником разрешений. Это не распределённая БД, не общий реестр всех VPS и пока не связанный отзыв токена подписки.

## Файлы и доверие

Для `/private/server.json` создаются:

- `/private/.server.json.devices.json` — реестр, `0600`;
- `/private/.server.json.devices-required` — маркер обязательности реестра, `0600`.

Каталог принадлежит выполняющему пользователю и имеет права `0700`. Реестр содержит секретные UUID. В автоматические снимки `.server.json.backups/` он **не включается**: восстановление старого Xray JSON не должно откатывать реестр.

Все операции CLI выполняются под тем же config lock, что и изменение Xray. Реестр записывается приватным временным файлом, fsync, атомарным rename и fsync каталога. Повреждение, исчезновение, symlink или неверные права реестра/маркера блокируют управление конфигурацией. Удаление файла реестра при сохранённом маркере не разрешает его повторную инициализацию.

Гарантия предполагает сохранность актуального доверенного реестра. Root или оператор, вручную удаливший оба файла либо заменивший их старой копией, способен обойти защиту. Криптографической защиты от отката самого реестра или независимого внешнего счётчика здесь нет. Для аварийного восстановления нужна отдельная свежая защищённая копия реестра и маркера; восстанавливать их старой версией вместе со snapshot запрещено.

## Новая конфигурация и миграция

`blackhole.cli init` создаёт реестр автоматически. Повторная инициализация не обнуляет историю отзыва, даже если основной JSON отсутствует.

Для существующей конфигурации требуется **явная однократная миграция**:

```sh
python3 -m blackhole.cli --config /private/server.json --xray /path/to/xray registry-init
python3 -m blackhole.cli --config /private/server.json list-devices
```

Перед миграцией оператор сверяет текущую конфигурацию с актуальным списком разрешённых устройств и историей отзыва. Нельзя инициализировать реестр из произвольного старого snapshot. Импортируются только согласованные пары имя/UUID обоих управляемых inbound с обычными полями генератора: `id`, `email`, для Vision — `flow`. Проверяется Xray. Неуправляемые VLESS/client-bearing inbound и нестандартные поля клиентов отклоняются, чтобы не потерять дополнительные ограничения молча.

`list-devices` выводит внутренний ID, имя и состояние, без UUID и ключей. Идентификаторы устройств и имена также остаются в приватной операторской среде. Повторный `registry-init` существующего либо повреждённого реестра запрещён.

Если создание реестра прервалось после записи маркера, операции прекращаются: сначала восстановите доверенное состояние отдельно. CLI не предлагает «забыть историю» для обхода ошибки.

## Добавление и отзыв

```sh
python3 -m blackhole.cli --config /private/server.json --xray /path/to/xray add-client phone
python3 -m blackhole.cli --config /private/server.json --xray /path/to/xray revoke-client phone
python3 -m blackhole.cli --config /private/server.json --xray /path/to/xray reconcile
```

Добавление сначала регистрирует устройство, затем публикует проверенную конфигурацию. Если публикация прервалась, повтор с тем же именем использует уже зарегистрированный активный UUID; новые записи не создаются при каждом повторе. Уже присутствующее в конфигурации имя по-прежнему отклоняется как дубликат.

Отзыв сначала **надёжно сохраняет tombstone** в реестре, затем удаляет UUID из обоих управляемых inbound и публикует конфигурацию. Повторный отзыв известного устройства безопасен. Отзыв по имени затрагивает историю этого имени. Повторная выдача ранее отозванного имени создаёт новый внутренний ID и новый UUID; старый UUID остаётся отозванным. История автоматически не удаляется.

Это две записи, не общая ACID-транзакция. Если реестр обновлён, а Xray отклонил кандидат или произошёл сбой диска, CLI возвращает ошибку; старый файл/работающий Xray ещё может разрешать доступ. `validate` обнаруживает расхождение с реестром. `reconcile` заново строит разрешённые списки из реестра, валидирует и записывает файл. После этого отдельно применяется выделенная служба Xray.

CLI не перезапускает службы и не завершает старые сессии. Запись отзыва сама по себе не доказывает немедленную блокировку трафика. При неуспешном применении состояние считается незавершённым, а не успешным отзывом на узле.

## Восстановление snapshot

```sh
python3 -m blackhole.cli --config /private/server.json --xray /path/to/xray restore REVISION
```

1. Прочитать snapshot и **актуальный** реестр.
2. Заново собрать списки клиентов обоих управляемых inbound только из `active`-записей.
3. Исключить старые отозванные и незарегистрированные UUID, даже если snapshot их содержит.
4. Сохранить также активные устройства, выпущенные после snapshot.
5. Проверить согласованность с реестром и настоящий `xray run -test`, сохранить прежний JSON и атомарно опубликовать результат.

Публичный низкоуровневый `save_validated` также отклоняет противоречащую реестру конфигурацию, если реестр/маркер уже существуют. Новый неподключённый к реестру путь не следует использовать для управления действующим узлом. Изменение путей, прямой запуск старого файла через Xray и обход CLI находятся вне этой защиты.

Восстановление возвращает прочие параметры snapshot (ключи REALITY, порты, маршруты). Их совместимость с текущими профилями требует отдельной проверки; реестр защищает разрешения устройств, а не гарантирует доступность старой транспортной конфигурации.

## Проверка

Тесты покрывают отзыв → восстановление старой копии, сохранение второго активного устройства, повторную выдачу имени с новым UUID, сбои публикации и повторное применение, пропавший/повреждённый реестр, отказ повторной миграции, попытку записи старого JSON через API и неуправляемый inbound.

Сетевые испытания и ограничения фиксируются в [отчёте](validation-results.md). Общие [транзакции конфигурации](config-transactions.md) и [план эксплуатации нескольких VPS](production-roadmap.md) описывают следующие этапы: применение службы с health-check, единый authority для узлов и согласованный отзыв подписок.

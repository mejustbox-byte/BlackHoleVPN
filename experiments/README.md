# Протокол шести этапов проверки

Статус: весь шестиступенчатый протокол не выполнен. Отдельно подтверждена передача данных через оба транспорта с внешнего Linux-клиента на один VPS; см. [результаты и ограничения](../docs/validation-results.md). Автоматический отчёт только суммирует данные, введённые оператором; он не запускает Xray, не проверяет достоверность данных и не решает, можно ли выпускать сервис.

## Общие условия

Тестовая инфраструктура с доступом к консоли и резервными копиями. Два сервера у разных провайдеров, одноразовые тестовые учётные данные, контрольная HTTPS-точка, Windows и iOS с зафиксированными версиями клиентов; Wi-Fi и мобильная сеть добровольного участника. Не проводите тесты с настоящими пользователями до проверки защиты данных. Не включайте перенаправление на прямой интернет, если ожидается защищённое соединение.

В каждом сравнении меняйте одну характеристику, проверяйте с одинаковой сетью и версией и повторяйте измерения в разное время. Заранее согласуйте число повторов и критерии успешности, отмечайте недоступность условий как `not_run`. Сохраняйте реальные IP, UUID, адреса подписки, имена и ключи только в защищённом месте вне репозитория. Обезличенные метки не должны позволять восстановить личность.

1. **Транспорты:** XHTTP stream-one и TCP Vision на одном сервере. Для каждого проверьте подключение, передачу небольшого файла в обе стороны, стабильность и восстановление; HEAD/204 сам по себе недостаточен.
2. **Серверы:** повторите этап 1 на втором сервере, используя эквивалентную конфигурацию и версии. Отметьте общие зависимости (провайдер, ASN, DNS, контрольная точка).
3. **Fingerprint:** сравните firefox и альтернативу в той же сети, для одного транспорта и версии клиента. Запишите результаты, а не вывод о гарантированном обходе.
4. **Фрагментация:** с ней и без неё на одной связке; зафиксируйте параметры, успех и влияние на задержку и передачу. Используйте только функции, совместимость которых проверена в конкретной версии клиента.
5. **Клиенты:** Windows и iOS, Wi-Fi и мобильная сеть. Проверьте доступ, смену сети, TUN и DNS/IPv6 отдельно; точные версии храните в отдельном защищённом отчёте.
6. **Подписка и отказ:** на изолированной установке проверьте обновление, ошибочный ответ, недоступность узла, откат и отзыв UUID. Токен подписки и UUID отзываются отдельно. Для проверки утечек используйте контролируемые конечные точки и проверенный механизм клиента; только после подтверждения всех сетевых путей фиксируйте результат.

## Сводка обезличенных результатов

Скопируйте `examples/trial-results.json` в приватное расположение и замените вымышленные строки измерениями. Каждая строка описывает одну попытку и содержит строго `stage`, `case`, `network`, `client`, `status`, `latency_ms`. Метки — короткие обезличенные буквенно-цифровые имена, не IP или URL; `status` — `pass`, `fail` или `not_run`; `latency_ms` — число для успешных измерений либо null. Ограничение формата не обнаруживает все возможные секреты: перед публикацией проведите ручную проверку.

```sh
python3 -m experiments.matrix /private/trial-results.json
python3 -m unittest discover -s tests -v
```

`not_run` не входит в знаменатель успешности; при отсутствии измерений доля успеха равна null. Медиана рассчитана только для числовых значений успешных попыток. Метрики не доказывают наличие DPI и не заменяют независимую проверку. Результаты текущей тестовой среды: модульные тесты с реальным Xray и передача данных через оба транспорта на одном VPS с внешнего Linux-клиента. Windows, iOS, вторая площадка и целевые мобильные сети пока не проверены.

Отдельное испытание экспорта JSON: XHTTP и TCP/Vision с FinalMask `tlshello` и без него передали реальные данные с внешнего Linux-клиента. Это частичная проверка совместимости для этапа с фрагментацией; повторяемые сравнения в целевых сетях, захват трафика и Windows/iOS остаются `not_run`. См. [подробные результаты](../docs/validation-results.md).
